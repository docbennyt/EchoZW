# DR-179 controlled Google onboarding

The protected `CALENDERZW_PRODUCTION_GOOGLE_ONBOARDING` environment secret is optional. The production release validates it and installs the `GOOGLE_PRODUCTION_ONBOARDING` Worker binding. Absence, expiry, a different deployed SHA or any invalid field denies the scope. Global Google delivery remains disabled.

The JSON contract is defined in `server/googleOnboardingPolicy.ts`. Every scope binds `candidateSha`, `ownerId`, `timetableId`, `revision`, `connectionGeneration`, `issuedAt` and `expiresAt`. The lifetime from issuance is at most 24 hours. Creation and update limits sum to at most 32, remote deletions are zero and provider requests are bounded at 40.

1. A new subscription may be prepared only in `mode=new`, `phase=enroll`, with `subscriptionId`, `calendarIdHash`, `deliveryRevision` and `deliveryGeneration` null. The existing subscription/profile transaction is serialized for that owner and timetable. Retries reuse the fresh pending record. An older connection requires its existing recovery path.
2. Before consent, select the returned subscription ID and install `phase=connect` through protected configuration. Fresh subscriptions use their actual generation, currently zero. For `mode=reconnect`, name the existing subscription and bind `calendarIdHash` to the SHA-256 of its exact existing remote calendar ID. Existing owner authorization and stored OAuth state still apply.
3. The callback persists renewed credentials and durable delivery intent. This phase grants no remote delivery authority. The student page reports pending delivery until convergence is verified.
4. After consent, read the committed job's exact desired revision and requested generation and bind them as `deliveryRevision` and `deliveryGeneration` in `phase=deliver`. Delivery must check that credential `updated_at` is at or after `issuedAt`, together with the current connection, publication and delivery fences. Reconnection retains the existing remote calendar. New-calendar delivery must claim creation under the current queue lease before the provider insert.
5. Execute the bounded canary through protected operations and verify remote contents and an idempotent retry before any wider authorization. Remove the temporary Worker binding and protected scope secret through the protected process, then verify binding absence. Expiry also denies further work.

Apply `20261106190719_google_calendar_onboarding_fences.sql` only after review through the approved migration process. It adds two nullable marker columns to the existing delivery jobs and service-only functions. A calendar insert with an uncertain provider or database result leaves its creation marker set. Queue retries and renewed OAuth consent cannot clear it or create another calendar. An operator must verify the remote outcome and recover the existing calendar identity through an audited operation before that connection proceeds.

Rollback disables the optional scope and retains subscription records, credentials, existing calendar IDs and creation markers. Removing the marker columns while an outcome is uncertain would lose the duplicate-creation protection.
